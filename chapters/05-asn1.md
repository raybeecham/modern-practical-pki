# Chapter 5: ASN.1

[Back to README](../README.md)

## Goal

Understand what ASN.1 is and how it defines the structure of cryptographic
objects such as keys, certificates, and certificate requests.

ASN.1 stands for Abstract Syntax Notation One. It is a standard syntax for
describing data structures. In PKI, ASN.1 is used heavily in RFCs to define
objects such as:

- Public keys.
- Private keys.
- Certificate signing requests.
- X.509 certificates.
- Certificate revocation lists.
- OCSP messages.

ASN.1 describes the structure. Encoding rules such as DER describe how that
structure is turned into bytes.

## ASN.1 and Encodings

ASN.1 is not the same thing as DER or PEM.

- ASN.1 defines the data structure.
- DER is a binary encoding of ASN.1 data.
- PEM is Base-64 text armor around DER data.

That is why PKI files often look like this:

```text
ASN.1 structure -> DER bytes -> PEM text
```

## Tag, Length, Value

DER-encoded ASN.1 data is built from TLV objects:

```text
Tag | Length | Value
```

- Tag: what type of value this is.
- Length: how many bytes are in the value.
- Value: the actual encoded content.

For example, an ASN.1 INTEGER encoded as DER starts with tag byte `02`.

```text
02 01 05
```

Read that as:

```text
02 = INTEGER
01 = length is 1 byte
05 = value is 5
```

Try it inside the container:

```bash
mkdir -p lab/chapter5
printf '\x02\x01\x05' > lab/chapter5/integer5.der
openssl asn1parse -inform DER -in lab/chapter5/integer5.der -i
```

Expected output:

```text
    0:d=0  hl=2 l=   1 prim: INTEGER           :05
```

## Type Classes

ASN.1 has four classes of types:

- Universal.
- Application.
- Context-specific.
- Private.

The first tag byte uses bits 8 and 7 to identify the class:

| Class | Bits 8-7 | Meaning |
| --- | --- | --- |
| Universal | `00` | Standard ASN.1 types such as INTEGER and OCTET STRING |
| Application | `01` | Types defined for a specific application |
| Context-specific | `10` | Types whose meaning depends on where they appear |
| Private | `11` | Types defined privately by an organization or system |

The first tag byte also includes:

- Bit 6: primitive or constructed.
- Bits 5-1: tag number, when the tag number is small enough to fit there.

Constructed means the value contains other ASN.1 objects. A SEQUENCE is a common
constructed type.

## Common Universal Types

Common ASN.1 universal types include:

| Type | Tag Byte | What It Represents |
| --- | --- | --- |
| INTEGER | `02` | Whole numbers |
| BIT STRING | `03` | Bits, often used for public keys and signature values |
| OCTET STRING | `04` | Raw bytes |
| NULL | `05` | Explicit empty value |
| OBJECT IDENTIFIER | `06` | Identifier for algorithms, extensions, and named objects |
| UTF8String | `0C` | Unicode string encoded as UTF-8 |
| PrintableString | `13` | Restricted printable character string |
| IA5String | `16` | ASCII string, often used for DNS names and email addresses |
| UTCTime | `17` | Time format with a two-digit year |
| SEQUENCE / SEQUENCE OF | `30` | Ordered collection of ASN.1 objects |
| SET / SET OF | `31` | Unordered collection of ASN.1 objects |

`PrintableString` has tag byte `13` in hexadecimal, which is decimal `19`.

`SEQUENCE` and `SET` are constructed types. Their values contain other ASN.1
objects.

## Object Identifiers

An OBJECT IDENTIFIER, or OID, names an object. PKI uses OIDs constantly.

Examples:

```text
2.5.4.3        commonName
2.5.4.10       organizationName
1.2.840.113549 rsaEncryption
```

The important idea: an OID is a structured number that identifies what
something means.

## DER Encoding

DER stands for Distinguished Encoding Rules. DER is a strict binary encoding for
ASN.1 data.

DER is important in PKI because signatures need exact bytes. If the same ASN.1
structure could be encoded in multiple valid ways, signature verification would
become messy. DER solves this by requiring one canonical encoding.

Simple DER INTEGER example:

```text
02 01 05
```

Read it as:

```text
02 = INTEGER tag
01 = length is 1 byte
05 = value is 5
```

A small DER SEQUENCE containing that INTEGER looks like this:

```text
30 03 02 01 05
```

Read it as:

```text
30       = SEQUENCE tag
03       = SEQUENCE value is 3 bytes long
02 01 05 = INTEGER 5
```

Try it inside the container:

```bash
printf '\x30\x03\x02\x01\x05' > lab/chapter5/sequence.der
openssl asn1parse -inform DER -in lab/chapter5/sequence.der -i
```

Expected output:

```text
    0:d=0  hl=2 l=   3 cons: SEQUENCE
    2:d=1  hl=2 l=   1 prim:  INTEGER           :05
```

## PEM Encoding

PEM is a text format. It wraps Base-64 encoded DER with header and footer lines.

The general shape is:

```text
-----BEGIN TYPE-----
Base64-encoded DER data
-----END TYPE-----
```

For example, certificates commonly use:

```text
-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
```

The important idea: PEM is easier to copy, paste, email, and store in text
files. The actual ASN.1 structure is still inside the DER bytes.

## ASN.1 Parsing

OpenSSL can parse DER and PEM objects with `openssl asn1parse`.

Parse a DER file:

```bash
openssl asn1parse -inform DER -in lab/chapter5/sequence.der -i
```

OpenSSL shows:

- Offset: where the object starts.
- Depth: nesting level.
- Header length: bytes used by tag and length.
- Value length: bytes used by the value.
- Primitive or constructed.
- ASN.1 type.
- Value, when OpenSSL can print it.

Example output:

```text
    0:d=0  hl=2 l=   3 cons: SEQUENCE
    2:d=1  hl=2 l=   1 prim:  INTEGER           :05
```

Read that as:

- At offset `0`, OpenSSL found a constructed SEQUENCE.
- At offset `2`, inside the SEQUENCE, OpenSSL found a primitive INTEGER.
- The INTEGER value is `05`.

## Key Takeaway

ASN.1 is the blueprint. DER is the binary encoding. PEM is the text wrapper.

When we inspect certificates and keys later, we are usually looking at ASN.1
structures encoded as DER and often stored as PEM.
